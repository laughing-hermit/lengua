# Review of work split into pieces (W20)

This review was written with the design and the code, by the author of both: it is not an
independent review. It lists what a program could try, and what could go wrong by itself, once
an idea may grant a program to split its work into pieces that run at once; the defence against
each; and the test that holds the defence. Paths are relative to the repository. The tests were
written with the defences, so none failed before its defence existed. To see them fail, one
commit that never reaches main takes the defences out; "The tests seen failing" at the end says
which commit and which run.

## What changed

Before W20 a program was one run on one core. Now an idea may say:

| Line | Imports |
|---|---|
| `- Splits: its work into up to 8 pieces, each of up to 1048576 bytes, each gives back 8192 bytes` | `lengua_split_1` `split(input, input_len, pieces, output, output_len)` and `piece()` |

A piece is a run of the program's own module from `_start`, in a store of its own
(`src/wasm/host/split.rs`). The pieces of a call run on threads of lengua's, at once; since
2026-11-12 the threads are kept through a run, and a piece reads its share from the program's
memory, lent for the call (R3 and R4).

The attacker is the program: the agent writes main.wat, and lengua treats it as untrusted. A
second attacker is a folder someone hands the user, whose idea `check` reads and whose tests
it runs. And one thing here is no attacker at all: the computer, whose cores and whose
scheduling differ from run to run, must change nothing of a result.

## Data races

### R1. Two pieces write the same memory, or a piece writes what the program reads

- Try: a piece writes at an address the program or another piece reads.
- Defence: there is no shared memory to write. A piece's store has its own linear memory, as
  the module declares it, zeros and its data segments; a piece's bytes arrive as its standard
  input, a copy; its answer leaves as a copy of what it printed. The engine's threads feature
  stays off, and main.wat can't declare a shared memory or use an atomic (the validator and
  the determinism rule refuse them, as before).
- Test: `a_piece_has_its_own_memory_and_reaches_nothing` (tests/wasm_split.rs): the program
  writes a byte in its memory before it splits, and the piece reads a zero there; the piece
  writes a byte in its memory, and the program reads a zero there afterwards.

### R2. A piece reads another piece's bytes, or the program's

- Try: a piece reads past its share, to learn what another piece got.
- Defence: the same. A piece's memory holds nothing of the program's input but what it read
  from its own standard input, which ends after its share.
- Test: `the_answers_come_in_the_pieces_order_however_the_pieces_run`: each piece's answer is
  its own bytes and no more, for an even cut, an uneven one and no bytes at all;
  `the_cut_covers_every_byte_once` (src/split.rs) holds the cut itself.

### R3. A piece sees what the piece before it on its thread left (2026-11-12)

- Try: nothing; it would happen by itself once the threads are kept through a run, if a
  thread kept a piece's memory or globals for the next.
- Defence: a thread keeps nothing of a piece. Each piece is a new store of the engine's, made
  for it and dropped with it: its memory is the module's first memory, zeros and data
  segments, and its globals the module's. The threads are all a run's pieces share.
- Test: `no_piece_sees_what_another_left` (tests/wasm_split.rs): four pieces each read a byte
  and a global of their own, then change both; one after the other on one thread, and at
  once, each finds them as the module declares them.

### R4. A piece reads the program's bytes after the call, or while they change (2026-11-12)

- Try: nothing a program can try; a fault of lengua's would do it. Since 2026-11-12 a piece
  reads its share straight from the program's memory, which lengua lends to the pieces'
  threads for the call (`lengua_os::lent`, the one place with unsafe code).
- Defence: the bytes are lent read-only, and a read copies from them inside their bounds.
  Nothing writes them during the call: the program waits in it, and a piece has no way to its
  memory. `lend` returns only once every holder has let go, so no thread reads them after
  the program runs on; a holder that never lets go makes it wait, not return.
- Tests: `lent_bytes_are_read_from_other_threads_until_the_call_returns` (crates/lengua-os);
  `the_answers_come_in_the_pieces_order_however_the_pieces_run`, where each piece's answer is
  its own share and no more; `split_work_gives_the_same_on_one_core_and_on_many`
  (crates/lengua-run/tests/alone.rs), on 20 MiB in three parts.

## Reach

### G1. A program splits without the idea's line

- Try: import `split` or `piece` in an idea with no `- Splits:` line; call them anyway in a
  module `check` never saw.
- Defence: rule 3 refuses the import; the host answers `NOTCAPABLE` before it looks at a
  buffer, and runs nothing.
- Tests: `the_checker_holds_main_wat_to_the_ideas_line` and
  `a_call_outside_the_ideas_line_is_refused` (tests/wasm_split.rs).

### G2. A piece reaches what the idea grants the program

- Try: a piece reads the clock, random bytes, a file, the network, or starts a program, so that
  its answer differs from run to run or it does work the user can't see in order.
- Defence: a piece's policy is made anew (`Policy::for_a_piece`): standard input and the split's
  own grant, nothing else. Every other call answers `NOTCAPABLE`, or what a program without
  the grant gets.
- Test: `a_piece_has_its_own_memory_and_reaches_nothing`: with `the clock` in the idea, a
  piece's `clock_time_get` answers `NOTCAPABLE`.

## Resource exhaustion

### X1. A fork bomb: pieces that split

- Try: call `split` in a piece, so that pieces grow without end.
- Defence: `split` answers `NOTCAPABLE` in a piece, and a piece's host holds nothing to split
  with. So a run has at most the line's pieces at once, and never more than 64.
- Test: `a_piece_has_its_own_memory_and_reaches_nothing`: a piece that splits gets
  `NOTCAPABLE`.

### X2. More pieces, longer pieces or more room than the line grants

- Try: call with 65 pieces, a piece of a gibibyte, or room for answers the line doesn't give.
- Defence: `Grant::covers` holds every call to the line: 1 to its pieces, none longer than its
  bytes, room for exactly its bytes back from each (`INVAL` otherwise). `check` refuses a
  call whose number of pieces isn't a named constant the line covers, and an idea's line
  outside 2 to 64 pieces, 1 to 1 GiB a piece and 1 to 65,536 bytes back.
- Tests: `a_grant_covers_a_call_inside_its_bounds`, `a_line_outside_the_bounds_is_refused`
  (src/split.rs); `a_call_outside_the_ideas_line_is_refused`,
  `the_checker_holds_main_wat_to_the_ideas_line`,
  `the_idea_holds_the_line_to_the_rest_of_the_idea` (tests/wasm_split.rs).

### X3. Memory: each piece has a memory of the module's size

- Try: declare a memory of 1 GiB and split into 64 pieces.
- Defence: `check` refuses a module whose pages, times the line's pieces and one more, pass
  16,384: a program and its pieces hold at most 1 GiB together. Each piece's store is held to
  the module's declared memory, one instance, one memory, as the program's is. A piece's
  answer is held to the line's bytes and its standard error to 64 KiB.
- Tests: `the_checker_holds_main_wat_to_the_ideas_line` (26,000 pages refused, 8,450 taken);
  `a_piece_that_fails_ends_the_run_as_the_first_in_order_ended` (an answer a byte past its
  room ends the run as output past its limit).

### X4. A call for each few bytes

- Try: split a few bytes at a time in a loop, to spend the computer on starting pieces.
- Defence: none beyond what holds any host call: rule 2 bounds the loop, and the run's
  deadline holds the whole. A program that does this is slow, as its tests' cost shows.
- Test: none of its own.

## Non-determinism

### N1. The answers come in the order the pieces end

- Try: nothing; it would happen by itself where a later piece ends first.
- Defence: each piece's answer is kept by its place, and written at its place once every
  piece has ended.
- Test: `the_answers_come_in_the_pieces_order_however_the_pieces_run`: the first piece spins
  for 20 million rounds before it answers, and its answer is still first.

### N2. The result depends on how many cores the computer has

- Try: nothing; it would happen where the cut, or the order, followed the cores.
- Defence: the cut depends on the length and the number of pieces alone (`split::cut`), which
  the program gives as a named constant. The cores decide only how many pieces run at once.
- Tests: `the_answers_come_in_the_pieces_order_however_the_pieces_run` runs the same input
  with the pieces at once and one at a time, the last first, and compares the bytes and the
  count of operations; `split_work_gives_the_same_on_one_core_and_on_many`
  (crates/lengua-run/tests/alone.rs) runs the example on 20 MiB with one piece at a time,
  three at once and one for each core, by lengua-run; every test `check` runs of a program
  that split runs a second time with the pieces one at a time, the last first
  (`check_one`, src/testrun.rs), on all five runners in
  `every_webassembly_program_goes_from_its_request_to_done`.

### N3. Which failure ends the run depends on which piece failed first

- Try: two pieces fail differently; the run ends as whichever the scheduler ran first.
- Defence: the run ends as the first piece in the pieces' order that didn't exit with code 0.
  A piece after one that failed is not started, or is stopped; a piece before it runs to its
  end, since it may fail too and then comes first. Nothing is written to the output.
- Test: `a_piece_that_fails_ends_the_run_as_the_first_in_order_ended`: the second piece exits
  with code 7 at once, the first with code 9 after 5 million rounds, and the run exits with 9,
  with the pieces at once and one at a time.

### N4. A test's count of operations differs from run to run

- Try: nothing; a piece that was stopped early would count fewer.
- Defence: a run counts its own operations and those of the pieces up to the first that
  didn't end well, each of which ran to its own end.
- Test: `the_answers_come_in_the_pieces_order_however_the_pieces_run` (the same count both
  ways).

## Deadline evasion

### D1. Work hidden in pieces outlives the run's time

- Try: pieces that never end, in a test or in the `run` tool, whose time is bounded.
- Defence: a piece's store has the run's own deadline and the run's own stop, which the
  engine's epochs look at every 10 ms; the pool still kills a worker 20 seconds after its
  job's time.
- Test: `the_runs_deadline_stops_its_pieces`.

### D2. A piece that trapped leaves the others running

- Try: one piece traps while the others never end.
- Defence: once a piece didn't end well, every piece after it in the order is stopped at the
  next epoch, and those not started aren't.
- Test: `a_piece_that_fails_ends_the_run_as_the_first_in_order_ended`: the first piece
  traps, three never end, and the run ends as trapped within the test's 15 seconds, of a
  limit of 30.

A run from a shell has no deadline and its engine stops nothing, as before W20: a piece
that started there runs to its end. `a_run_from_a_shell_runs_its_pieces` holds that such a
run runs its pieces and ends as a piece that trapped; no test has pieces that never end
there, since nothing would stop them but the user.

## Secrets

### S1. A secret in one piece changes what another can time

- Try: pieces run beside each other on cores that share caches; one piece's work on a
  secret changes how long another's takes, which the program can learn where it has a clock.
- Defence: no secret crosses into a piece, since a program that splits names none: an idea
  with a `- Splits:` line and a `- Secret:` line is refused, before any code is read. The
  secret rule and the check of the machine code are as they were for every other program.
- Test: `the_idea_holds_the_line_to_the_rest_of_the_idea`.

## What this review doesn't cover

- The engine's own safety with several stores at once on several threads: trusted, as the
  engine is.
- The time a piece takes as a channel between the pieces of a program with a clock and no
  secret: a piece has no clock, and the program sees only when all have ended.
- A proof of the join: the step that joins the answers is tested, not proven.
