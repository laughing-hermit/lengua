# Review of what a program reaches beyond the network (W18, second part)

This review was written with the design, before the code, by the author of both: it is not an
independent review. It lists what a program could try once an idea may grant it files the user
names, programs to start, and the terminal's mode; the defence against each; and the test that
holds the defence. Paths are relative to the repository. The threat cases were written first
(the first commit of the branch `wip/reach-2` holds them alone), and the tests were written with
the defences, so none failed before its defence existed. To see them fail, one commit that never
reaches main takes the defences out; "The tests seen failing" at the end says which commit and
which run.

## What changed

Before this part a program reached files only beneath its working folder, started nothing, and
could not change the terminal's mode. Now an idea may also say:

| Line | Import |
|---|---|
| `- Files: reads the file its first argument names` (also `writes`, `reads and writes`; `the files its arguments name`) | `lengua_fs_1` `file_open(argument, mode, out_fd)` |
| `- Files: reads the folder its first argument names` (also `reads and writes`) | `lengua_fs_1` `folder_open(argument, out_fd)` |
| ``- Runs: `hostname` with no arguments`` (also ``with the arguments `-tf`, a value and up to 4 values``, `, within 60 seconds`) | `lengua_run_1` `program_run(command, command_len, input, input_len, output, output_len, out_size, out_code)` |
| `- Uses: the terminal` (the line was there; its imports are new) | `lengua_term_1` `term_is(fd, out)`, `term_size(out_columns, out_rows)`, `term_raw(mode)` |

The attacker is the program: the agent writes main.wat, and lengua treats it as untrusted. It is
steered by what it reads: a file's bytes, a started program's output, a key. The user saw the
idea's grants, and typed the arguments; the program must reach nothing past them. A second
attacker is a folder someone hands the user, whose idea `check` reads and whose tests it runs.

## Files and folders the user names

The design: the program never writes a path. It gives the place of one of its arguments, and
lengua reads that argument, which the user typed, and opens what it names. A grant names the
argument (`first` to `ninth`, or every argument) and says `reads`, `writes` or both.

### F1. A path the program chose

- Try: build a path from a file's contents or from a response, and open it; open `/etc/passwd`
  or `../../.ssh/id_rsa` under a grant of the first argument.
- Defence: `file_open` and `folder_open` take a number, the argument's place, and no text.
  The path is the argument's own bytes, which lengua holds (`Host::args`), never the program's
  memory. `named::Grant::covers` (`src/named.rs`) holds the place to the grants.
- Tests: `wasm::host::named::tests::only_the_arguments_the_idea_names_are_opened`;
  `checker::wasm::tests::rule_3_takes_the_files_and_programs_only_as_the_idea_grants_them`.
- What would fail: with `covers` always true, the second argument opens under a grant of the
  first.

### F2. Writing where the grant says reads, reading where it says writes

- Try: open the first argument for writing, or with `TRUNCATE`, under `reads the file`; make a
  file, remove one or rename one in a folder granted with `reads the folder`.
- Defence: `named::Grant::allows` holds the mode to the grant before anything is opened; a
  folder opened without `writes` is a root that refuses every change (`Files::writes`,
  `src/wasm/host/files.rs`: `path_open` to write or make, `path_create_directory`,
  `path_remove_directory`, `path_unlink_file`, `path_rename` answer `NOTCAPABLE`).
- Tests: `named::tests::a_mode_the_grant_does_not_say_is_refused`;
  `named::tests::a_folder_granted_for_reading_takes_no_change`.
- What would fail: the file is emptied, and the folder gains a file.

### F3. lengua's own folders, and the system's

- Try: the user is led to type, or an agent passes, lengua's data folder (its `key` signs every
  lock), the folder of compiled modules (the engine runs what it finds there), a folder that
  holds one of them, such as the home folder, or a file inside one; `/proc/self/mem`,
  `/proc/<pid>/environ`, `/sys/...`, `/dev/sda`, on Windows `\\.\PhysicalDrive0`, `CONIN$`, a
  named pipe.
- Defence: `named::forbidden` compares the place, with its links followed, with lengua's own
  folders, which the run hands the host (`Job::own`, `Here::own`): a named file may not lie in
  one, and a named folder may not be one, hold one or lie in one, as the working folder may
  not. `/proc`, `/sys` and `/dev` are refused on Linux and on macOS alike. On Windows a place
  that isn't on a drive or a share (`\\?\C:\…`, `\\?\UNC\…`) is refused, which takes the device
  namespace and the pipes. What opens must be a regular file, or a folder for `folder_open`.
  The program hears `NOTCAPABLE`, and the run's report says why.
- Tests: `named::tests::lenguas_own_folders_and_the_systems_are_never_opened`;
  `tests/wasm_named.rs` `a_run_opens_no_file_of_lenguas_own`.
- What would fail: the key's bytes are read.

### F4. Links

- Try: a handed folder holds `notes.txt`, a symbolic link to a private file, and the user names
  it; a hard link to a file outside; a link planted between the check and the open.
- Defence: the folders on the way are the user's path, which the system resolves as it does for
  any program the user runs; lengua follows them once (`canonicalize`), holds the result to F3,
  and says the place it found before the program starts. The last name is never a link: lengua
  looks at it without following (`symlink_metadata`), opens it beneath the folder it resolved
  (cap-std), and then holds the file that opened to be a regular file with one name (the
  hard-link rule of the working folder, `link_count`), before it is emptied when it was to be.
  In a named folder every rule of the working folder holds: no link is followed, names are
  byte-exact and held to every system's rules, and a file with two names isn't opened.
- Tests: `named::tests::a_link_at_the_last_name_is_not_followed`;
  `named::tests::a_file_with_two_names_is_not_opened`.
- Open: a link another process plants at the last name between lengua's look and its open is
  followed beneath the same folder, as in the working folder (the host's review, still open
  there).

### F5. A test that reaches the user's files

- Try: an idea whose tests give the argument `/home/user/.ssh/id_rsa`, or `../../x`, so that
  `check`, which runs a handed folder's tests, reads or writes it.
- Defence: in a test every named path is resolved beneath the test's own fresh folder, by the
  working folder's rules (`names_in`): one that starts at the root or climbs out is
  `NOTCAPABLE`, and nothing outside the folder is looked at. Only `run` resolves a path on the
  user's file system.
- Tests: `named::tests::a_tests_paths_stay_in_the_tests_folder`; `examples/copy` goes from its
  idea to done on every runner.

### F6. Size, count and time

- Try: write without end to the file the user named; open the same argument thousands of
  times; read a huge file.
- Defence: a named file is a file descriptor like any other: the run's file limits
  (`Limits::file_write`: 64 MiB a file and 256 MiB in all in a test and in `run`'s own
  temporary folder), the 4,352 descriptors, the deadline between pieces of a write and before
  each buffer of a read. A named folder's listings count against the 1,048,576 entries.
- Tests: `named::tests::a_named_file_is_held_to_the_runs_file_limits`.
- Open: a run from a shell has no file limit, in a named file as in the working folder.

### F7. Which argument is a path

- Try: under `the files its arguments name`, an option such as `--key=…` is opened as a path.
- Defence: none is needed: every argument is the user's own text, and a file that isn't there
  is `NOENT`. The grant line says every argument may be opened, and `check` and `run` say it.

## Starting named programs

The design: `program_run` takes the program's name and its arguments, each ended by a NUL,
starts it, gives it the input bytes, waits until it ends, and gives back what it printed and
its exit code. Nothing stays behind: no process and no descriptor.

### R1. A program the idea doesn't name, or arguments it doesn't bound

- Try: run `rm`; run the granted `git` with `--upload-pack=…`, with one more argument, or with
  an argument that starts with `-` in a place the idea leaves to the program.
- Defence: `starts::Rule::covers` (`src/starts.rs`): the name must be the rule's, each argument
  the rule writes must be that text byte for byte, and the count must be the rule's. A place
  the rule leaves to the program (`a value`, `up to N values`) takes 1 to 255 bytes of text
  with no control character, and never one that starts with `-` or `/`, so a value is never an
  option on any system. Refused with `NOTCAPABLE` before anything is looked for.
- Tests: `starts::tests::a_rule_covers_its_command_and_no_other`;
  `wasm::host::start::tests::what_no_rule_covers_is_not_started`.
- What would fail: the stand-in for the refused command runs and its output comes back.

### R2. A shell

- Try: an idea that names `sh`, `bash`, `cmd`, `powershell`, `env` or `xargs`, with the
  command in a value; a granted name that is a link to a shell.
- Defence: `starts::Rule::read` refuses a line that names a shell or a program that only
  starts another (the list `SHELLS`), with or without `.exe`, in any case. `starts::found`
  looks at the file it resolved, with links followed, and refuses one whose own name is on the
  list. lengua starts the file itself (`std::process::Command`), never through a shell, and on
  Windows only a `.exe`, never a `.bat` or a `.cmd`, which `cmd` would run.
- Tests: `starts::tests::a_line_never_names_a_shell`;
  `starts::tests::a_name_that_resolves_to_a_shell_is_not_started`.
- Open: a program that runs what its arguments say (an interpreter with `-c`, `find -exec`)
  is as wide as the arguments its line writes. lengua has no list of them; the user reads the
  line, which `check` and `run` show.

### R3. A program the program wrote

- Try: with `- Uses: files`, write an executable named `hostname` into the working folder, or
  a library the started program loads, then run it.
- Defence: lengua finds the program itself: only the absolute folders of `PATH`, never a
  relative one, and never a file that lies in the run's working folder, in a folder the user
  named, or in the system's temporary folder (`starts::found`). The started program's current
  folder is an empty folder lengua makes for the call and removes after it, so nothing the
  program wrote is beside it.
- Tests: `starts::tests::a_program_is_found_only_in_the_absolute_folders_of_the_path`;
  `start::tests::a_program_in_the_working_folder_is_not_started`.

### R4. What the started program inherits

- Try: read the user's environment (tokens, keys) through a started `env`-like program; reach
  the starter's descriptors (its connections, its files, the worker's line to the server).
- Defence: the environment is empty (`env_clear`); on Windows it holds `SystemRoot` alone, with
  the system's own value, without which Windows's libraries don't load. Standard input is a
  pipe with the bytes the program gave, standard output a pipe lengua reads, standard error
  nothing. No other handle is inherited: every handle lengua holds is close-on-exec (Rust's
  standard library opens them so) or not inheritable.
- Tests: `start::tests::a_started_program_gets_no_environment_and_its_input`.

### R5. Time and output without end; processes left behind

- Try: start a program that never ends, prints without end, or starts another and exits.
- Defence: a call lasts the rule's seconds at most (10 unless the line says `within N
  seconds`, 1 to 600) and never past the run's deadline; the output is the program's buffer at
  most. Past either, lengua ends the started program and every process it started: its
  process group on Linux and macOS (`killpg`), its job on Windows (a job object, closed with
  `KILL_ON_JOB_CLOSE`, `lengua_os::Job`). The call answers `TIMEDOUT` or `FBIG`. One call runs
  at a time: `program_run` returns when the started program has ended.
- Tests: `start::tests::a_started_program_ends_at_its_time`;
  `start::tests::a_started_program_prints_at_most_the_buffer`.
- Open: on Windows a process is put in its job right after it starts, so one it starts in that
  moment is outside the job. On Linux and macOS a started program that makes a process group
  of its own leaves it.

### R6. A test that starts a real program

- Try: an idea whose tests make `check` run `rm` with arguments the user never saw.
- Defence: in a test nothing is started. A test's step says what a command prints and its exit
  code (``the program `hostname` prints `box` and exits with code `0` ``), every test of the
  idea sees those, and a command no step gives is `NOENT`, as on a computer without the
  program. Only `run` starts a program.
- Tests: `start::tests::a_test_starts_nothing`; `examples/computer` from its idea to done.

### R7. A started lengua program

- Try: start `lengua-mcp run other` to act with another idea's grants, or with the starter's.
- Defence: nothing is special about it. `lengua-mcp run` holds the program it runs to that
  program's own lock and idea, whoever started it, and the starter's grants aren't inherited:
  the started process has no descriptor and no environment of the starter's.
- Open: with an empty environment `lengua-mcp` finds no data folder, so a line must pass
  `--data-dir` as an argument for it to run at all. There is no test of it.

### R8. A secret in a command

- Try: put a secret in the started program's arguments, which other processes of the computer
  can read; choose the command by a secret.
- Defence: the secret rule (`src/checker/wasm/secret.rs`): the command is a buffer the host
  reads that isn't data, so a secret in it is refused. The input is data, as `sock_send`'s
  bytes are, and once a secret was sent what comes back is secret.
- Test: `checker::wasm::tests::a_secret_never_names_a_command`.

## The terminal

### T1. The terminal left in raw mode

- Try: set raw mode and trap, exit, run past the deadline, or be stopped with Ctrl-C.
- Defence: the host keeps the mode the terminal had (`term::Terminal`) and puts it back when
  the host is dropped, which every end of a run reaches: `_start` returning, `proc_exit`, a
  trap, the deadline, lengua's stop. For what ends the process without that, lengua_os puts the
  mode back from a handler: `SIGINT`, `SIGTERM`, `SIGHUP` and `SIGQUIT` on Linux and macOS, the
  console's control events on Windows. Raw mode leaves the interrupt key on, so Ctrl-C still
  ends the program.
- Tests: `term::tests::the_mode_is_put_back_on_every_end` (exit, trap, deadline);
  `lengua_os::terminal` tests against a pseudo-terminal on Linux and macOS, and against a new
  console on Windows.
- Open: `SIGKILL`, and a power cut, restore nothing.

### T2. The terminal without the grant

- Try: import `term_raw` without `- Uses: the terminal`.
- Defence: the checker's import rule, and the host again at every call.
- Tests: `checker::wasm::tests::rule_3_takes_the_files_and_programs_only_as_the_idea_grants_them`;
  `term::tests::without_the_grant_nothing_is_set`.

### T3. A test or a tool's run that touches a terminal

- Defence: only a run from a shell has a terminal. In a test and in the `run` tool the three
  functions find none: `term_is` writes 0, the others answer `NOTTY`.
- Tests: `term::tests::a_test_has_no_terminal`; `examples/key` from its idea to done.
