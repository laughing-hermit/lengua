# Review of a call between modules (W23, the rest)

This review was written with the code, by the author of both: it is not an independent review. It
says what a module that a lengua program calls can reach and what it can't, what holds each
limit, and the test of each. Paths are relative to the repository. The tests were written with
the defences, so none failed before its defence existed. To see them fail, one commit that never
reaches main takes defences out; "The tests seen failing" at the end says which commit and which
run.

## What changed

Until now a run was one module in one store: `main.wat`'s build, or `main.wasm`, an outside
module that is the program itself (outside-2026-11-12.md). An idea's `- Calls:` line now puts
more modules in the store, up to 4: an outside module, which a compiler made from another
language, or the module of another lengua program, which lengua checked on this computer and
whose idea offers functions with an `- Exports:` line. Each is an instance of its own
(`src/wasm/host/call.rs`).

The new surface is small, and each piece of it is listed here:

1. the functions the idea's line names, linked to the program's imports, WebAssembly to
   WebAssembly, with numbers alone in a call;
2. two functions of the host, `give` and `take` of `lengua_call_1`, which copy bytes between
   the program's memory and a called module's, and which only the program can call;
3. `check`'s reading of a called outside module (`src/wasm/outside.rs` `read_called`), and its
   opening of a called program (`src/server/calls.rs`);
4. one more line in lengua.lock, `calls`, and the run's check against it;
5. the exports a lengua program may have, where the rules allowed `_start` and `memory` alone.

The attacker is a called module: a compiler's honest output with a bug, or bytes written by hand.
It is steered by the numbers and the bytes the program gives it. A second attacker is the
program's own `main.wat`, as before, which now has a module to use as a tool.

What a called module must not do:

1. reach anything of the computer, whatever the program's idea grants the program;
2. read or write the program's memory, or another called module's;
3. run past the deadline, hold more memory than its module declares, or use more stack than the
   engine gives the run;
4. crash or hang lengua-mcp or lengua-run;
5. be another module than the one the program's tests ran with;
6. make a reply, a lock or a run say more than "trusted, not proven" of an outside module, or
   "checked" of a lengua program that is not checked here.

## A lengua program's exports

The rules let `main.wat` export `_start` and `memory` alone. With an `- Exports:` line they let it
export the functions the line lists, each its own, with the listed type
(`structure.rs` `exports`, `offered`). Three things follow.

- **An exported function takes numbers, never an address.** The memory rules hold a function to
  what it reaches through the addresses its callers lend it, by checking each caller. A caller
  in another module is checked by no rule of this one, and its numbers name nothing in this
  memory. So `check` refuses an exported function that uses a parameter as an address
  (`src/checker/wasm/mod.rs` `offered`): it works in `main.wat`'s own regions alone.
- **Its proofs are of its own tests.** An exported function is proven as far as the library's
  own `_start` calls it. A call from another program, with other numbers, is held by the rules
  that hold every function (bounded loops, the memory rules, assertions), and by the engine to
  the library's own memory. What the rules leave to a proof, such as an index held by an
  assertion, is not proven for a caller's numbers: the assertion stops the run instead.
- **It reaches no host as a called module** (C1). An assertion that fails in a called library
  calls `fd_write` to say its number, and the run ends there, as "a module the program calls
  called a function of lengua's host". The number is not printed.

An exported function is a root for the lint of functions never called
(`src/checker/wasm/rules.rs`): a library may offer a function its own `_start` doesn't call. Such
a function is held to the rules and run by no test of the library.

## The threat cases

### K1. A called module calls the host

A module built for WASI imports `fd_write`, `path_open` or `proc_exit` and calls it from a
function the program calls. `check` refuses the module for the import. Were the reading skipped,
the import links to a function that stops the run, and nothing is written, opened or exited.
Tested with the program's idea granting files, which the called module still doesn't get.
Tests: `tests/calls.rs` `a_called_module_reaches_no_function_of_the_host` (the host alone, the
reading skipped), `check_refuses_a_called_module_lengua_does_not_take` (the reading).

### K2. A called module reads or writes the program's memory

It can't name it: its loads and stores are in its own memory. Test:
`a_called_module_has_a_memory_of_its_own` (the same address is two bytes).

### K3. The program copies outside a memory

`give` and `take` with bytes past the called module's memory, at its last byte and one past it,
with a module the idea doesn't call, with a module that has no memory, with a length of zero at
the end, and with the program's own buffer outside its memory. Test:
`a_copy_stays_inside_both_memories`. A program whose idea calls nothing gets `NOTCAPABLE`:
`a_program_whose_idea_calls_nothing_copies_nothing`.

### K4. A called module never ends, or calls without end

A loop in a function, a loop in a start function, and a function that calls itself. Test:
`the_deadline_and_the_stack_bound_a_called_module`.

### K5. A called module takes memory

`memory.grow` to its maximum, past it, and a load past its last byte. Test:
`a_called_module_keeps_to_the_memory_it_declares`. `check` refuses a memory with no maximum or
one past 1 GiB: `check_refuses_a_called_module_lengua_does_not_take`.

### K6. Another module than the one the idea names, or another type

The module is missing from the run, has another name, lacks a function, or exports it with
another type. Test: `a_run_starts_only_beside_the_modules_its_idea_names`. `main.wat` imports a
function the line doesn't name, with another type, or from a module the idea doesn't call:
`main_wat_calls_only_what_its_idea_names`.

### K7. The module is changed after `check`

The file is replaced with another module that has the same functions, or removed. `run`,
`lengua-mcp run` and lengua-run refuse the program. Test:
`a_called_module_changed_since_check_does_not_run`.

### K8. A called program that is not the one lengua checked

Its main.wat is changed, its lock is damaged by one digit, its lock is removed, or it is checked
again with other code. Each time the caller doesn't run, by the `run` tool or from a shell.
Tests: `a_called_program_is_verified_before_it_is_loaded`,
`a_called_program_is_checked_and_offers_the_functions`.

### K9. An exported function reaches through a caller's number

Test: `main_wat_exports_what_its_idea_offers_and_takes_no_address`, with an export the line
doesn't list and a listed function that isn't exported.

### K10. A reply that says more than is so

Tests: `a_program_that_calls_an_outside_module_says_what_is_trusted` (the reply, the next step,
no entry in `verified`, the lock, the runs' words, the attester),
`a_program_calls_a_lengua_program_that_lengua_checked` (`checked`, and never `trusted`),
`a_proof_stops_at_a_call_and_holds_before_it` (the proofs).

### K11. A secret, and split work

Test: `an_idea_that_calls_names_no_secret_and_does_not_split`.

### K12. The tools of a run

A trace, a profile and a stop each run a calling program as any other. A trace shows what
crosses the host's edge, which a call of a called function does not: it has `give` and `take`
with their numbers, and says so. A profile's sample inside a called module is counted for the
function and line of `main.wat` that called it, since the module's functions have no names in
`main.wat`. Test: `the_tools_of_a_run_work_with_a_program_that_calls`.

## What is left open

- **What a called module computes.** An outside module's answers are the program's inputs, and
  the program's tests show them only for the runs they made. lengua says so.
- **The same bits everywhere.** A called module has no clock and no random bytes, since it has
  no host, and the engine's NaNs are canonical. lengua claims nothing more of an outside module.
- **A trap's place in a called module.** A trap there is placed at the line of `main.wat` that
  made the call, with the words "it trapped inside a module it calls". The module's own place is
  not shown.
- **Time and memory are the run's, not the module's.** A called module can use the whole of the
  run's time and the engine's stack; there is no budget for the module alone. Each module's
  memory is its own cap, so a program with 4 modules may hold 5 GiB in all.
- **A run from a shell has no deadline**, for any program.
- **`_initialize`** of a called module runs at the start, as WASI's libraries expect; `_start`
  of a called lengua program never runs, so what its `_start` would set up is not set up.
- **The attester and `verified`** do nothing for a program that calls a module.
- **A module that the program is, calling another.** `main.wasm` with a `- Calls:` line is
  refused: lengua can't hold an outside module's imports to an idea's line by a rule.
- **A called program that calls.** An idea with `- Exports:` has no `- Calls:` line.
- **The export surface for another host.** A lengua module's exports are ordinary WebAssembly
  exports, so another host can instantiate the module and call them, but lengua ships no host
  library and no native build for that, and nothing but lengua checks the lock.

## The tests seen failing

The commit 65825da, kept as the tag `archive/wip/library-off` and never merged, takes these out
together: C1 and C2 (a called module is given the program's host), C4 (a copy is held neither to
the idea nor to the called module's memory), `check`'s reading of a called module, C10 and C11
(a run holds no called module to the lock and no called program to its state), C5 and the
rule for an exported function's parameters in the checker, C14 and C15 at the idea, and the
refusal of an entry in `verified` and of the attester (C12).

Run 43303937905, tests/calls.rs on Linux on x86-64 at that commit: 10 of its 21 tests fail, the
tests named under K1, K3, K6 (`main_wat_calls_only_what_its_idea_names`), K7, K8
(`a_called_program_is_verified_before_it_is_loaded`), K9, K10
(`a_program_that_calls_an_outside_module_says_what_is_trusted`) and K11, with
`check_refuses_a_called_module_lengua_does_not_take`. The same file at the branch's own head
passes 21 of 21 (run 43303909259).

Not shown failing:

- K2, K4 and K5: what holds there is the engine's own (an instance's memory, the epoch, the
  stack, a memory's declared maximum), which lengua has no switch to take out.
- `a_run_starts_only_beside_the_modules_its_idea_names`, the proofs' stop at a call, the lock's
  line and the tools: their code stayed in.
- K9's rule for an address has a narrow reach: an exported function that its own module also
  calls with a number is refused by the memory rules first (M1), as the first runs of the test
  showed. The rule speaks for a function that only other programs call.
- Each defence by itself: the commit takes them out together.
